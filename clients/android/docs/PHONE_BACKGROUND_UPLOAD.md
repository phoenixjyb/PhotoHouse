# Phone batch uploads while the screen is locked

**Delivery — October 19:** [phone v73](PHONE_V73_RELEASE_2026-10-19.md) is published
on Windows HTTPS OTA. Production build/profile, signature/icon and complete APK
readbacks passed. Physical Samsung lock-screen transfer acceptance remains open.
The implementation and historical test details below retain their original scope.

## October 19 source candidate (v73)

The released v72 app deliberately pauses the batch queue from
`MainActivity.onPause → ConnectedStore.background`. Locking the screen therefore
interrupts uploads even when network and server are healthy. Unlocking restores
the encrypted metadata queue, but never starts another transfer automatically.

The v73 source separates the private UI lifecycle from a user-started batch
runner. Start, Resume and Retry promote a non-exported `dataSync` foreground
service before running the queue. The production store is owned once per app
process, avoiding duplicate queue owners after Activity recreation. Foreground
execution is the Android mechanism for noticeable ongoing work; Android 14
requires its service type and corresponding permission. See
[service types](https://developer.android.com/develop/background-work/services/fgs/service-types)
and [launch rules](https://developer.android.com/develop/background-work/services/fgs/launch).

## User experience and controls

- The folder/file review explains that batch uploads can continue while locked.
- A generic progress notification shows byte/item progress and Pause. It includes
  no filenames, library names, accounts, media or credentials. Lock-screen public
  content contains only a generic upload message.
- On Android 13+, an explicit optional button requests upload notifications.
  Denying notifications does not grant or revoke upload consent; Android's
  foreground task controls still apply. The notice explains that the user can
  reopen PhotoHouse to Pause, or stop it with Android's active-app controls.
  The UI queue remains available.
- Notification Pause is tied to its run ticket. An older notification command
  cannot cancel a later explicit Resume.
- Pause, logout, session expiry, changed account/credential or revoked destination
  access fences the runner. Covering the private UI still clears previews and
  stops microphone/voice interaction.
- A partial wake lock is renewed only during an active transfer. A session is
  limited to two hours, then pauses; the user may explicitly resume. There is no
  boot receiver, sticky restart, battery-optimization bypass or automatic consent
  restored from queue metadata.

## Recovery and private data

The existing protocol, request/batch IDs and server-offset reconciliation remain
unchanged. Completed files are not uploaded again. After an interrupted process,
reopen the app and Resume: the queue queries the server before sending more bytes.
Original media remains with the selected document provider. Queue metadata stays
encrypted in app-private storage; credentials and locators never enter service
Intents. A memory-only ticket connects the explicit UI request to its service.

The picker reports failures to retain a document-provider read grant. Such a
provider may require reselecting unfinished files after process termination.
This does not authorize re-uploading previously completed files.

## Acceptance boundaries

Core tests cover default foreground-only behavior, the explicit lease, covered
UI, foreground revalidation and revocation/expiry. QA service instrumentation uses
generated bytes and an in-memory API, drives the real MainActivity callbacks,
recreates/backgrounds that Activity during a transfer, and tests notification
Pause, explicit offset-preserving Resume and stale Pause delivery. Its injected
store is accepted only in the separate QA package on an emulator. It never
contacts the family server.

Build/lint, emulator results, physical Samsung lock behavior, signing and OTA
publication are separate gates. This source document alone claims none of them.

## Physical phone check after publication

1. Verify the installed release includes this change. Reopen the existing batch;
   use Resume rather than selecting its completed files again.
2. Allow progress notifications, start the transfer and note the received bytes.
3. Lock the phone for two minutes while keeping the same network, then unlock.
   Confirm the received count advanced without tapping Retry.
4. Pause from the upload notification. Confirm progress stops, then explicitly
   Resume and check it continues from the server's saved offset.
5. Reopen completed items and confirm their server receipts. If Android ends the
   process, reopen PhotoHouse and Resume; process termination is a recovery case,
   separate from keeping the screen locked.

Until a verified release is installed, keep the phone unlocked during large
uploads. A source or emulator result does not establish Samsung battery-policy
or real network behavior.
