# November 24 audit: reconciliation and delivery plan

The owner-provided repository audit correctly identifies a stale public `main`
and the need to consolidate existing work before expanding the architecture.
Its pinned GitHub state is a historical source inventory, not a current Windows
service inventory or permission to activate features.

## What changed after the audit

The newer local line already contained substantial November Web, Search and
Rust work. Commit ancestry alone did not establish equivalent capabilities:
phone proposal adoption existed through reworked components, but protected TV
story approval and Rust profile registration were missing from that line.

The integration retains the Rust branch's history, exact core implementation,
nonempty Windows benchmark data and original five provenance records. The
historical records are preserved unchanged in
[the provenance archive](provenance/RUST_STACK_HISTORY_2026-11-20.json); the active
source ledger separately verifies current integrated bytes. Current package
hardening and the phone editor are retained. Protected TV approval is reconciled
against current client interfaces, with a default guest-only build and separate
opt-in HTTPS origin. No installed APK, signing, OTA or physical acceptance follows
from this source integration.

The bilingual `/roadmap/` was separately delivered on Windows and confirmed by
the owner. Its final result passed 16 existing HTTPS checks and nine metadata
route checks. Native jobs, streams, owned temporary controller cleanup and the
actual offline/local audit completed. A lost transport response was recovered
from its exact existing result archive without replaying deployment. The natural
grouping binding result was `REFRESH_DEFERRED`, zero updates; it is not a completed
index sweep or household-quality result. Current runtime and source deployment
continue to be reported separately.

Family LAN importing also has prior delivery evidence. This does not establish
native Android/iOS background backup or secure pairing as completed products.

## Concrete defects closed in the integration source

- A bare exact reviewed place answer could be rejected by Search v2 instead of
  narrowing the prior search. The new path retains person/date/media/text and
  still revalidates current access and source.
- Month-only corrections in Search v2/v3 could switch to the current year. They
  now use the active search's unique year; explicit years take precedence and
  ambiguous multi-year ranges still clarify.
- A blank story suggestion could overwrite authored text in a chapter without
  selected sources. The editor preserves unchanged wording and applies AI
  attribution only to a real wording change. Review, explicit save and identical
  retry after an uncertain save remain separate actions.
- One failed Jude capability read could leave the composer unavailable until a
  page reload. An explicit reopen can retry a transient failure through the
  existing scoped restore gate, without creating a turn, conversation or capture.
- The standard source archive omitted the roadmap module and assets. Fixed
  immutable Git-source mappings and supported source/bundle root resolution now
  close that dependency. Extracted smoke requests both language pages and all
  five actual asset bytes, with checkout fallback denied.

These fixes were subsequently [delivered on Windows](RELEASE_2026-11-24_FUNCTIONAL_FIXES.md)
from merged main `c7a28ef`, retaining the original base runtime and qualified
native kernels. The first transaction rolled back after a pre-worker scheduler
snapshot timeout; the corrected no-console launch passed, followed by actual
HTTPS and natural SYSTEM grouping handoff checks and explicit owned release.
Grouping deferred work with zero updates, so this is not a full index sweep or
real-model relevance result. Overlapping local cohorts must not be summed into
a larger claimed test total. Optional TV approval remains uninstalled here.

## Where the audit needs qualification

The proposed search, voice and relevance targets require an agreed dataset,
hardware, denominators and representative samples. They do not silently replace
frozen historical contracts, and subjective prose or aspirational latency must
not again block unrelated functional delivery. Access, source integrity,
cancellation, resource bounds and explicit editorial actions remain hard limits.

The current Rust installation/binding evidence is narrower than full household
quality, but stronger than a blanket statement that all Rust work is merely an
uninstalled proposal. Likewise, generated browser or native-component tests do
not establish usability on a family's phone, TV, microphone or library.

No general superiority over PhotoPrism is claimed. Competitive specifications
should be refreshed from primary documentation when used for a concrete product
comparison. A family knowledge graph, event understanding, iOS backup and a
permission-aware external interface remain staged opportunities, rather than
reasons to replace the current backend or database.

### Generated Search request timing

Twenty runs per source used the same three-turn Chinese journey and a fresh
generated SQLite fixture per run. The first turn selected September photos,
the second requested videos, and the third shifted the same video filter to
October. The baseline and candidate returned identical filter and result
shapes. This measures the in-process API with a reviewed fixture index and no
model or listener. It leaves native model timing and real library scale open.

| Request | Baseline `1867686` median / p95 | Candidate `c9ad331` median / p95 |
| --- | ---: | ---: |
| Start a search | 9.710 / 11.703 ms | 9.366 / 11.298 ms |
| Change media on the same thread | 10.115 / 10.459 ms | 9.589 / 10.677 ms |
| Change month on the same thread | 9.787 / 10.368 ms | 9.476 / 9.804 ms |

On a separate **25,000-asset generated library** at `2d41f0b`, six three-turn
trials with the standard read caps returned the expected complete totals
and paged results. The five warm runs had medians of **873 ms**, **987 ms**,
and **998 ms** for the same three steps. The result is from the in-process
protected API and does not measure a model or the home network. Five warm
samples are too few for a representative p95.

Two matched runs per source compared the later discovery read path at the same
scale. Each run used one cold and five warm three-turn trials. Result totals
and the page's asset IDs, kinds, recorded dates, and thumbnail fields matched.
The change parses each recorded date once and builds the encoded library
thumbnail query once per projection. Each call still authorizes the user and
checks the current source.

| Request | Range of baseline warm medians | Range after removing repeated work |
| --- | ---: | ---: |
| Start a search | 859–955 ms | 680–682 ms |

### Generated photo-viewer timing

Eight runs per source alternated the same generated photo and a fixed 250 ms
description response delay. Chromium's page clock measured from click to photo
decode. The median was **295.2 ms** (288.2–300.1) at `0f1130b` and **38.0 ms**
(32.2–47.4) at `2d41f0b`. The test uses an in-process generated service and
measures the dependency on the description request. Home-network, phone and
representative-library timing remain open.
